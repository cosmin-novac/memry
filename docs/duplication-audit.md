# Duplication audit

Date: 2026-07-24

This is a review list, not authorization to remove more features. PostgreSQL was the only
duplicate implementation removed in this change because that removal was explicitly
decided. Every item below needs a separate product decision and migration plan before code
is deleted.

| Priority | Duplicate or overlap | Verified current state | Why it is costly or confusing | Clean option for a later decision | Risks and disadvantages of that option |
|---|---|---|---|---|---|
| High | Mem0 selectable backend plus the production SQLite backend | `Config.backend` and `build_backend()` let the whole product run through `Mem0Backend`, but that adapter lacks episodes, temporal invalidation, normalized topics, entities, relations, collections, and complete audit behavior. `MemoryBackend` consequently supplies many silent no-ops. | It recreates the parity problem that made PostgreSQL expensive, while the product cannot honestly offer the same guarantees in Mem0 mode. New features can appear to work but silently lose state. | Remove Mem0 as a runtime backend and move the comparison into an isolated eval/import-export adapter. Then make production backend capabilities required rather than optional no-ops. | Removes an advertised interop path and may affect anyone currently setting `MEMRY_BACKEND=mem0`. An export/migration story and usage evidence are needed first. |
| High | Persisted `Memory.entities` strings plus authoritative `EntityMention` links | Every memory stores a JSON string list from extraction, then the entity resolver writes exact mention rows. Graph retrieval and entity APIs use mentions; the JSON list is not repointed on entity merge and cannot distinguish same-name identities. | Two representations can disagree, and the less precise one leaks into exports and the Mem0 adapter. It invites new callers to use names where stable entity IDs are required. | Make `EntityMention` canonical, project entity display names into API/export responses when needed, migrate old string-only records into mentions where safe, then remove the stored JSON column. | Existing exports and clients may expect the `entities` field. Historical rows may not be safely disambiguated, so migration needs an explicit unresolved state rather than guessed identity. |
| High | Three network authentication entry paths | The server accepts one configured admin key, configured tenant keys, and runtime account/OAuth keys; dashboard sessions add a cookie path. They converge on `Principal`, but provisioning, rotation, persistence, and recovery differ. | Operators must understand several overlapping identity systems, and security behavior needs tests across every path. Static secrets cannot be managed through the product. | Choose runtime accounts as the canonical tenant identity store, retain one documented break-glass/bootstrap admin mechanism, and migrate static tenant definitions into accounts. | Makes the smallest single-user deployment less configuration-only, requires secret migration, and needs a safe recovery workflow if the account database is damaged. |
| High | `memry.db` and a separate `auth.db` | Both product data and account/OAuth state use SQLite, but they are separate files, locks, transactions, backup steps, and reset lifecycles. The separation originally kept auth independent of selectable memory backends; SQLite is now the sole production store. | A business operator can restore memories without identities or vice versa. There is no atomic backup across the two files, and the old backend-independence benefit is much smaller. | Put account and OAuth tables in the production SQLite database under a clear schema prefix and provide a one-time `auth.db` migration. Preserve commands that reset memories without deleting identities. | Increases the blast radius of one corrupt or mishandled file, couples auth and memory migrations, and makes reset semantics more delicate. The migration must be crash-safe and reversible. |
| Medium | Standalone MCP-over-HTTP server and the combined `memry serve` `/mcp` endpoint | `memry mcp --transport http` starts FastMCP directly, while `memry serve` mounts the same tool server inside Starlette alongside REST, dashboard, accounts, and OAuth. The authentication behavior and available surrounding endpoints differ. | Two remote-server entrypoints double deployment documentation and auth/security test combinations without serving two distinct customer jobs. | Keep MCP stdio for local clients and make `memry serve` the only remote HTTP server. Deprecate the standalone HTTP flag before removal. | Existing scripts may rely on the standalone command or its simpler behavior. A deprecation window and equivalent host/port options are required. |
| Medium | Root Compose file and VPS Compose file | Both define and build the Memry service, data volume, environment, restart behavior, and port topology; the VPS version adds Caddy, health checks, and more configuration. | Shared service settings can drift, producing a local container that does not match the documented VPS product. | Keep one canonical Compose service definition and use a small VPS override/profile for Caddy and production-only settings. | Compose merge rules and relative build paths can be harder to understand than two explicit files; installer compatibility must be tested. |
| Medium | `SyntheticTag` rows plus normalized topic nodes and hierarchy edges | A synthetic record stores parent and source strings while `Topic` and `TopicRelation` now store the same parent/child structure and provenance. The old table still drives the synthetic API and duplicate-proposal suppression. | The hierarchy has two records to keep in sync, and string sources can drift from renamed topic IDs. | Move proposal provenance and creation time onto the topic/edge model, project the existing synthetic API from those rows, migrate records, then remove `synthetic_tags`. | The legacy record is a convenient immutable snapshot of what the LLM proposed. Removing it can lose proposal-level grouping unless that grouping is modeled explicitly. |
| Medium, temporary | `Memory.categories` JSON plus normalized `Topic`/`MemoryTopic` storage | Writes currently update both; reads and filters use indexed topic links. The JSON field is retained as a public compatibility projection and migration rollback path. | Permanent dual-write would create drift risk and retain JSON1/full-row update costs after the migration is proven. | Keep it only through a defined compatibility release, add parity checks and a repair command, then project `categories` from links at API/export boundaries and remove the JSON column/write. | Removing it is a storage migration and can break direct database consumers. Projecting topics adds a join to memory serialization unless batch-loaded efficiently. |
| Low | Public terminology `tags`/`categories` plus internal `topics` | The normalized model is called Topic, while stable public fields and several routes/CLI functions still say categories or tags for compatibility. The dashboard now says Topics. | Mixed vocabulary increases onboarding and makes searches/refactors noisier, though it does not duplicate data by itself. | Use `topic` internally everywhere, document `categories` as the compatibility API name, and introduce versioned topic-named endpoints before any old route is retired. | Renaming public fields or tools creates churn for integrations with little immediate customer value. Keep aliases until a real version boundary. |

## Mechanical duplicate check

An AST scan found no repeated function, method, or class definitions in `src/`. The only
byte-identical source files are three intentionally empty package `__init__.py` markers;
they are not competing implementations and need no cleanup.
## Reviewed overlaps that should stay

| Overlap | Decision | Reason |
|---|---|---|
| Entity description plus linked memories | Keep | The description is a bounded rebuildable cache for orientation; linked memories are the auditable evidence. They have different jobs and explicit freshness rules. |
| Collections plus topics | Keep | Collections summarize emergent clusters; topics are deterministic classifications and filters. |
| Typed relation graph plus co-occurrence fallback | Keep | Typed edges are evidence-grounded facts; co-occurrence is a bounded fallback when old memories have no extracted edges and is not persisted as a competing truth. |
| Python, CLI, REST, MCP, and dashboard surfaces | Keep | They serve distinct integration and operator needs and route through the same `MemoryStore` logic rather than duplicating the memory engine. |
| Exact vector scan plus optional ANN sidecar | Keep | Exact scan is correct and fast for small/filtered sets; ANN is a rebuildable candidate accelerator for larger sets and is exact-rescored. |
